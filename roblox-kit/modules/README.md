# `roblox-kit/modules/` — the shared ModuleScript layer

35 ModuleScripts that a game copies into `ReplicatedStorage` (or `ServerScriptService`,
for the server-only ones) and requires by path. They are the reusable half of the kit;
`../systems/` holds the drop-in gameplay systems that are built out of them, and
`../prefabs/` holds ready-to-spawn instance trees.

Every module is **commercial-safe**: no game-specific nouns, no placeholder IDs that a
published game would have to hunt down, and no dependency on anything outside the Roblox
API except where this file says so.

## The copy rule, and its one exception

A module is copied into a game, never linked, and `browse_kit` / `install_kit_module`
treat each file as self-contained. That is why no module required another one before
v6.1.0.

**v6.1.0 exception:** `NetGuard.lua` and `NetworkGuard.lua` now require their sibling
`Throttle.lua`, because both hand-rolled a rate limiter and neither was reusable (see
[Rate limiting](#rate-limiting)). The kit has no linker, so the require is a plain
`script.Parent:FindFirstChild("Throttle")` guarded by an `assert` whose message names the
file to copy. Copy all three, or keep the older standalone versions.

## Rate limiting

Before v6.1.0 there were two independent rate limiters in the kit and no way to reuse
either:

- `NetworkGuard:CheckRateLimit` hand-rolled a **token bucket** (`tokens`, `lastRefill`,
  refill `elapsed * rate`, clamp at `burst`).
- `NetGuard.allowRate` hand-rolled a **fixed-window counter** (`start`, `count`, reset when
  the window rolls).

These are not two implementations of one thing — they make different promises, and a
caller who swaps one for the other silently changes how their limit behaves. So both
primitives moved into `Throttle.lua`, where each has a name, a spec and an injectable
clock:

```lua
local Throttle = require(path.Throttle)

local bucket = Throttle.new(10, 20)        -- 10 calls/s, burst 20, refills continuously
local window = Throttle.fixedWindow(8, 1)  -- at most 8 calls per 1s window, hard stop

local ok, retryAfter = bucket:attempt()    -- never yields
bucket:wait()                              -- yields until a token is available
bucket:peek()                              -- capacity left, consumes nothing
bucket:reset()
```

Defaults, applied whenever an argument is `nil`, `0`, negative, `NaN` or infinite: rate
`10`/s, burst `max(3, rate * 2)`, window limit `8`, window `1s`. A limiter that refuses
everything because somebody passed `0` is a worse accident than one that runs at the
documented default — an emergency stop is `FeatureFlags`' job, not a rate limiter's.

**What changed for existing callers:** nothing observable, with one deliberate exception.

- `NetworkGuard:CheckRateLimit(playerKey, endpoint)` makes the same allow/deny decisions
  as before (a fresh bucket starts full and the first `attempt` consumes one token, which
  is exactly the old `tokens = burst - 1` first call), still counts `violations` per key
  and still records a `rate_limit_exceeded` anomaly. It gained `:RetryAfter(playerKey,
  endpoint)`, and `NetworkGuard.new` accepts an optional `{ now = fn }` clock so a spec can
  drive it without sleeping.
- `NetGuard.allowRate(player, actionKey, maxCallsPerWindow, windowSeconds)` still returns a
  bare boolean and still allows exactly `maxCallsPerWindow` calls per window. It gained
  `NetGuard.rateRetryAfter(player, actionKey)`. **The exception:** the first limit and
  window given for an `actionKey` now govern it. Passing different numbers for the same key
  later used to mix the new limit with the old window's start — a caller bug that half
  applied; it is now ignored instead.

## Feature flags

`FeatureFlags.lua` exists so a system can be shipped dark and switched on without a code
change, a redeploy or a remote.

Flags are **attributes on a Folder named `ReplicatedStorage.FeatureFlags`**, so the server
writes one attribute and normal replication carries it to every client — no remote, no
polling, nothing to keep in sync.

```lua
local Flags = require(path.FeatureFlags)

Flags.configure(require(path.FlagsConfig))   -- { NewShop = false, PartyPlay = true }
if Flags.get("PartyPlay") then ... end       -- never yields, never creates the Folder
Flags.set("PartyPlay", false)                -- server only; clients read
local conn = Flags.onChanged("PartyPlay", function(on) ... end)
conn:Disconnect()
Flags.all()                                  -- effective map, for telemetry and debugging
```

The convention for a system that ships flags: put the defaults in **`shared/FlagsConfig.lua`**
as a plain `{ FlagName = boolean }` table and call `Flags.configure(...)` from the system's
server script. Because `shared/` is required by both sides, the client's defaults match the
server's before anything has been set, and a flag that has never been touched resolves to
the value the code says it has.

Rules that matter when reading the source:

- **Reading never writes.** `get` and `all` do not create the Folder; only `set` does, and
  only on the server. A place that never sets a flag never grows one.
- **Non-boolean attributes are ignored, not coerced.** In Lua the string `"false"` is
  truthy, so an attribute set from a text field would otherwise switch a feature *on*.
- `configure` is additive and may be called more than once (later calls win per key), so
  several systems can share the root. It returns how many defaults it applied, which is
  how a typo'd config table becomes visible.
- A listener registered **before** the Folder replicates fires once when it appears:
  attributes that were already set never fire `AttributeChanged`, so without that prime an
  early client would miss them.
- `onChanged` callbacks run in `pcall`; one throwing listener does not stop the others.

## Specs

`tests/*.spec.lua` are [TestEZ](https://github.com/Roblox/testez) specs, the layout
`../systems/CONVENTIONS.md` requires for pure modules. They are written so that they need
no running game: `Throttle.spec.lua` drives a fake clock (`{ now = fn }`) and never sleeps,
and `FeatureFlags.spec.lua` exercises the pure `resolve` plus flag names no real game would
use, so it neither creates `ReplicatedStorage.FeatureFlags` nor mutates the place.

Run them in Studio through the bridge's `run_studio_tests` tool, or from a Script:

```lua
local TestEZ = require(game:GetService("ReplicatedStorage").TestEZ)
TestEZ.TestBootstrap:run({ script.Parent.tests }, TestEZ.Reporters.TextReporter)
```

Setting a flag and watching it replicate is **not** covered by a spec — it needs a live
server, so it is operator-verified.

## Adding a module

1. Header comment: what it is, the API in a fenced block, and any non-obvious rule.
2. `--!strict` unless the module is a port of pre-existing non-strict code.
3. No game-specific nouns, and no dependency on another module unless it is declared here
   (see the copy rule above) and in the module's own header.
4. Pure logic gets a `tests/<Name>.spec.lua`.
5. Add the row to the index above, then run `python3 -B tools/emit_facts.py --check` from
   the repo root: the module count in `docs/FACTS.md`, `README.md`, `CONNECT.md` and
   `AGENTS.md` has to move with it.
