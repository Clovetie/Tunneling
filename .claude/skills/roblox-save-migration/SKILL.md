# Roblox save migration

Use when a live save format is about to change: a field is added, renamed, retyped or removed, a value changes meaning, a store is split or merged, or a release that already wrote new-format saves has to be rolled back. `roblox-data-reliability` covers persistence broadly and mentions migration; this skill is the deep end on **versioning**, and it assumes you have already read that one.

**Start by reading what the kit ships**, because it already answers this and installing a second persistence layer over a live one is how saves get destroyed: `roblox-kit/systems/core/data/` — `shared/DataConfig.lua` (`STORE_NAME`, `KEY_PREFIX`, `STUDIO_SUFFIX`, `DATA_VERSION`, `MIGRATION_BASELINE`, `PURCHASE_HISTORY`), `shared/DataTemplate.lua`, `shared/DataMigrations.lua` (the game-owned steps), `shared/SaveMigrations.lua` (the engine), `server/DataService.server.lua` (the wiring and status handling), and a vendored `server/ProfileStore.lua`. If your game uses `modules/DataStoreSafe.lua` instead, read `references/datastoresafe-gaps.md` first — that module has no migration step at all and two behaviours that will silently defeat one.

## What a migration must guarantee
1. **Migrate before reconcile.** This is the whole skill in one line, and the kit says it in a comment: `-- migrate before Reconcile, which would fill a missing dataVersion from the template`. If the template's current version reaches the row first, the engine sees `version == targetVersion`, returns `current`, and **no step ever runs** — every old save reads as already migrated while still holding the old shape.
2. **Steps run on a deep copy, and the copy only replaces the save when every step succeeded.** `SaveMigrations.Migrate` never modifies its input; it returns `"migrated", working` or a status with `nil`. A half-applied migration must not be persistable, so a step that errors leaves the original row untouched.
3. **Never remove a step.** `DataMigrations[v]` upgrades a version-`v` save to `v + 1` in place, and rows at version `v` exist in the wild forever. Deleting one turns those rows into `missingStep`, which kicks the player. Steps accumulate; they are history, not configuration.
4. **Refuse rather than guess.** `newer`, `missingStep` and `failed` all end the session **with the save untouched** and kick the player to rejoin. The untouched part is the guarantee — a refused migration must never write, or the refusal has corrupted the very row it was protecting.
5. **`reset` is only for below-baseline saves.** No `dataVersion`, a NaN version, or one below `MIGRATION_BASELINE` starts fresh from `DataTemplate`. That is a data-loss path reserved for pre-launch builds, so the baseline is a promise you make once and then keep.
6. **Idempotent, and safe on a fresh row.** A save may be migrated more than once — a failed cloud write, a second server, a rollback and re-rollout — and a step must produce the same result the second time. Steps must also be harmless on a brand-new defaulted row, because `reset` and a first-ever join both produce one.

## Rollback is a status, not a script
7. There is no down-migration here, by design. The `newer` status *is* the rollback story: an old server meeting a save written by a newer build refuses it, leaves it untouched, and kicks with "A newer version of the game is out! Please rejoin to play it." So rolling back is safe **only** if the old code refuses new saves instead of trying to read them — which is what makes writing the refusal path part of shipping the migration, not part of undoing it.
8. Note that `DataService` deliberately does **not** `warn` on `newer`, while it does on `missingStep` and `failed`. During a staged rollback, `newer` is expected traffic, not a defect; a log that treats it as an error trains everyone to ignore the two statuses that are real.
9. If a release wrote a format the previous build cannot read, the rollback plan is: stop the rollout, roll the code back, and accept that players who saved under the new build are refused until it returns. The alternative — a down-step — has to have been written and tested *before* the rollout, because afterwards the rows are already out there.

## Making a change
10. Bump `DataConfig.DATA_VERSION` from `v` to `v + 1`, then add `[v] = function(data) ... end` to `DataMigrations.lua`, upgrading a version-`v` save **in place**. Fields that are only *added* need no step logic — `Reconcile()` fills them from the template — but the version bump still needs an (empty) step, or every `v` save becomes `missingStep`.
11. Keep `dataVersion = DataConfig.DATA_VERSION` in the template and never rename `STORE_NAME` to change a format: a new name is a new, empty store, and every existing player silently becomes a first-time join.
12. Write the step as a pure function of the data table — no `game`, no services, no yields. That is what makes it testable at all (see Verification), and it is also what makes it reviewable: a step you cannot call from a spec is a step nobody has ever seen run.
13. Preserve fields you do not recognise. Rebuild only what you are changing; constructing a new table from the template erases every field written by a system you did not read.
14. For a destructive change (dropping or retyping a field that holds earned value), plan a backup copy, authorisation, and a rollout where old and new code coexist. Do not modify production DataStores or enable API access without explicit user authorization.

## Verification
Say which store you actually touched, because in Studio it is not the one you think.

- **Studio never touches production here:** `DataService` appends `DataConfig.STUDIO_SUFFIX`, so the store is `PlayerData_Studio`. A playtest with "Enable Studio Access to API Services" on really saves and really proves the round trip — for that store. With API access off, ProfileStore falls back to an in-memory store by itself, and a migration "verified" that way never met a DataStore at all. Report which of the two you had.
- **Provable from this repository alone:** `SaveMigrations.Migrate` is pure — deep copy in, statuses out, no DataModel and no yields — so its status table (`current`, `migrated`, `reset`, `newer`, `missingStep`, `failed`) can be pinned by a spec and replayed outside Studio, and the system can be parsed, type-checked and global-checked with `luau_check` and `tools/check_globals.sh`. That proves the logic, not persistence.
- **A known gap, stated rather than glossed:** `systems/core/data/README.md` promises `tests/SaveMigrations.spec.lua` and says it fails until every version from `MIGRATION_BASELINE` to `DATA_VERSION - 1` has a step — but the system ships **no `tests/` directory**, so that guard does not currently run. Writing the spec is the first task of any version bump here, and the `testez_first_workflow` prompt is the loop for it.
- **Needs an operator, with the exact command:** the README's Studio check — set `ReplicatedStorage.Tests:SetAttribute("RunTests", true)` in Edit, Play, then read the TestEZ output with `get_console_output` and expect `SaveMigrations` to report 0 failures; the refused-save drill — temporarily set `DataConfig.DATA_VERSION` one *lower* than the saved version and Play, expecting the "newer version" kick and an untouched save; and `run_testez_suite {"testsDir": "roblox-kit/systems/core/data/tests"}` once that spec exists (today it would find none, which is itself the finding).
- **Cannot be verified without a real deployment:** session locking across two live servers, `BindToClose` flushing on shutdown, DataStore throttling and availability, and rollback against rows already written by the new build. List each as unverified with the command that would settle it; never claim durability from a mock, a memory fallback, or a green static check.
